# Jev call — jev-plan-exit (style-library)

_Per-call definition from jev-call-template.md. Built 2026-11-14 (phase-guard augmentation pass 1). The judgment: a library update plan is only a plan when Execute and Verify are already checklists with instruments — and when the plan cannot produce this job's named deviation, STALE-VIEW: a registration or tier move landing while VIEWS.md still shows the old library to the production jobs that read it first._

## 1. What it judges
- Deliverable / surface judged: the cycle's Plan in RUN.md — the registration plan, the Execute checklist and the Verify checklist it produces, and its failure-point evaluation — against the Observe inventory that jev-observe-exit advanced.
- Call point: style-library INSTRUCTION §2, as its gate out. The phase advances on the verdict's recorded disposition (applied, or set aside with reason). An unfired call makes the cycle INCOMPLETE. Plan's named product, judged here: Execute checklist + Verify checklist (both in RUN.md) + failure-point evaluation.

## 2. Instruction (the model's charge)
Judge whether this Plan can be executed and verified without improvisation, for THIS library. Price, in order: (1) REGISTRATION COMPLETENESS — per landed packet the plan names the INDEX row fields (specimen · date · consumer · surface · technique count · reception pointer), the TECHNIQUES entries to add (one per catalogue technique, with packet + timestamps + frame filenames), the ASSETS extraction candidates it will put to jev-asset (extraction is a judgment, not a copy of the lessons table), each technique's obligation mark (OWED with queue position, or not-owed with its priced reason — never a silent exemption), and every tier entry/move with the scores.md evidence that carries it. (2) STALE-VIEW PREVENTION — if the plan changes ANY Feeds field, registers a technique, or moves a tier, the Execute checklist must contain the VIEWS.md regeneration step in this same cycle, derived from the amended Feeds fields + ASSETS consumer lines, with the derivation cross-check named in Verify; if the plan touches none of those, it must print that finding explicitly. A plan that would leave VIEWS.md showing production a library that no longer exists has failed at its named deviation class, whatever else it gets right — INDEX.md routes production to VIEWS first, so a stale view is the library lying at its front door. (3) CHECKLISTS AS PRODUCTS — the Execute checklist is complete against the registration plan (including broken-pointer repairs found in Observe, the board-gate step if §2.3 opened — catalogued count ≥3 while samples-board-DESIGN.md is still a stub — and the GROWTH.md daily entry if this is the day's first library cycle, production AND consumption side by side with the throughput line and the two-consecutive-growth headline check); the Verify checklist names an instrument per property, not an intention: pointer census (counted, not sampled, while the library is small) · existence audit on every row changed · views-derivation cross-check · consumption-claim check · tier-move evidence check · naive-use test with its target technique and its cold reader named (fresh subagent on the library surface only, or a timed self-pass printing its path; >60 s or a wrong landing is a FAIL with the failing step named). (4) FAILURE POINTS EVALUATED — the plan states what breaks it, priced for this job: a packet whose frames cannot be named (the TECHNIQUES entry is not written; the gap goes back to video-digestion as a hand-off entry — the plan must say so, not improvise the entry) · a tier claim whose scores.md does not carry it · a Feeds change with no regeneration slot in the cycle's time · a GROWTH entry tempted to print production counts alone · the naive-use target already tested so often its pass proves nothing (rotation priced: newest entry first, then least-recently tested). (5) REDUCTIONS NAMED — anything the objective or Amendments A1–A5 demand that this plan quietly drops (a registration field, the obligation mark, the consumption side of GROWTH, the board-gate check, the same-cycle VIEWS duty) is printed as a reduction with its reason, or the plan is hiding it; an unnamed reduction found here classifies the verdict. Score 0–1 per dimension and classify the primary defect.

## 3. Context contract (masked view)
- FED: the Plan as drafted in RUN.md (registration plan · Execute checklist · Verify checklist · failure-point evaluation) · the advanced Observe inventory with jev-observe-exit's profile · the TECHNIQUES.md Feeds/tier excerpts for every technique this plan touches · VIEWS.md's header + derivation note (what it was last derived from) · GROWTH.md's latest entry (whether a daily entry is owed, and the days-to-clear direction) · the board-gate state line.
- NEVER FED: the planner's rationale or effort prose · a tier's reputation from prior attempts (only the cited scores.md speaks) · reception data (popularity does not complete a checklist).
- Ceiling: ≤32k tokens; text only. Packing rule: feed the plan whole first; trim register excerpts to the touched techniques before ever trimming a checklist — a truncated checklist judged as complete is this call's worst misfire, so overflow fails preflight and the Plan is split, never silently shortened.

## 4. Output space
- Verdict classes: **EXECUTE · REVISE · RETURN-TO-OBSERVE**. REVISE keeps the cycle in Plan with the named fixes; RETURN means the inventory cannot carry this plan (a landing unpriced, a tier unevidenced) and §1 reopens.
- Dimensions (0–1): registration completeness (0.0 = packets planned in bulk prose · 1.0 = per-packet rows, entries, extractions, obligation marks and tier evidence all named) · stale-view prevention (0.0 = a Feeds/tier/registration change with no same-cycle VIEWS step · 1.0 = regeneration in the Execute checklist with its cross-check in Verify, or the no-change finding printed) · checklist instrumentedness (0.0 = Verify promises to "check" · 1.0 = every Verify item names its instrument, its count base, and its fail action) · failure-point coverage (0.0 = no failure named · 1.0 = this job's priced failure points each carried with their disposition) · growth pairing (0.0 = production counts planned alone · 1.0 = GROWTH/consumption/throughput duties present with the headline rule armed, or explicitly not owed this cycle with reason).
- Rejection taxonomy (one primary): STALE-VIEW (the plan would change Feeds, a tier, or the register without regenerating VIEWS.md in the same cycle — this job's named deviation class, Amendment A5) · CHECKLIST-GAP (an Execute or Verify checklist missing or incomplete against the registration plan) · VERIFY-BY-INTENTION (a Verify item with no instrument, count base, or fail action) · UNEVIDENCED-TIER-MOVE (a tier entry/move planned without its scores.md) · PRODUCTION-ONLY-GROWTH (a GROWTH duty planned without its consumption side or throughput line) · BOARD-GATE-MISSED (≥3 catalogued with the design stub unaddressed and unmentioned) · SILENT-REDUCTION (a demanded field, mark, or duty dropped without being named).
- Accepted profiles travel: the profile prints in RUN.md beside the gate line; Execute follows the checklists as judged, and any mid-Execute change to a checklist re-enters this gate for the changed items only, with the re-judgment recorded.

## 5. Floors and disposition
- stale-view prevention < 1.0 on any plan that touches a Feeds field, a tier, or the register → REVISE with primary class STALE-VIEW. (The floor is priced absolute because the defect is deterministic: if the step is absent, the view will be stale — a runner setting this verdict aside records that pricing as the miss.) · checklist instrumentedness < 0.6 → REVISE · registration completeness < 0.6 → REVISE, or RETURN-TO-OBSERVE where the shortfall is the inventory's, not the plan's.
- Disposition: the verdict is advisory — reviewed by the runner, applied or set aside with the miss recorded in Condense. The verdict, its primary class, and its disposition land in RUN.md either way.

## Call command
- Assemble the §3 context as one text packet (RUN.md Plan draft + the advanced inventory + the named excerpts, ≤32k) and fire it through the fleet's sealed Jev decision-model route with §2 as the instruction verbatim; record the raw verdict, the dimension profile, and the primary class in RUN.md before Execute opens. Until that route is bound for this job, the runner executes this file's §2 + §3 as the defined prompt-and-context assembly. **Firing: this call fires at its step on every cycle. A cycle in which it did not fire prints INCOMPLETE.**
