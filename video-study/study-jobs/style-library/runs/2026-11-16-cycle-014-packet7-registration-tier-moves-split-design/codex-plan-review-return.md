## The three answers (first section, per §2 of the review definition)

### (1) EXACTLY AS ASKED? — NO

The split axis is exactly §8's (by container family, seven files matching the VIEWS families), the design is the oversized cycle's Plan product as §8 prescribes, and it does not become a packet shelf — §5 refuses a packet-order split by name, and grouping stays container-first. But it is not exactly as asked on the evidence and tier terms: for every technique a reader meets outside its canonical family, packet evidence is no longer one step away (see (3)-a), and a DESCRIBED technique's tier is no longer co-located with its entry (see (3)-b). A design that delivers the grouping while lengthening the evidence path and separating the tier from the entry has delivered the split, not the owner's surface.

### (2) ANYTHING DIFFERENT? — YES

Cures named per deviation; until they land in the design, the claim that the design meets the owner's expectation is withdrawn.

- **D1 — Pointer lines are poorer than the view lines they parallel.** VIEWS.md lines (the derived surface this design re-points) carry `Item · Tier · What it gives · Source (P# @ timestamps)` on every line. The design's §2 pointer line carries only number · name · tier · canonical family file — no packet, no timestamps. Cure C1 (in (3)-a).
- **D2 — The Feeds vocabulary is not the clean seven families the mechanical generation assumes.** Measured over the register: alongside the seven clean labels, Feeds fields carry variant labels — first-named variants alone include `opening (hook)` (1), `opening (series design)` (1), `thumbnail (one-off)` (1), `cross-container` (2), `cross-container (system)` (1), and `all containers (system)` (2), with further variants in non-first positions (e.g. `ending (verdict moments)`). Design §4 step 1 ("parse every entry's Feeds field; write the full entry to its canonical family file") names no normalization map, so a mechanical generation would misfile, strand, or silently invent families for these entries; and `all containers (system)` entries feed every family, which the canonical-home + pointer rule does not price at all. Cure: the design must add a Feeds-label normalization table (every variant label in the register → its family file, with `all containers` priced explicitly: canonical home in cross-container + a pointer in each of the other six, or a stated alternative) and the migration census (§4 step 2) must count entries per variant label, not only per T##.
- **D3 — Family files are given no header spec at all.** The design specifies TECHNIQUES.md's post-split header in detail but says nothing about what a family file's header carries: no per-family tier counts, no packet keys, no substrate rule, no plain-language family label beyond the filename. INDEX's new route sends a production reader VIEWS → family file → packet, i.e. the family file is a landing surface in its own right; an unspecified header is a hand-maintained surface waiting to happen. Cure C2/C3 (in (3)-b/(3)-c).
- **D4 — The post-split Locator's form is unspecified.** §2 keeps "the Locator" in TECHNIQUES.md, but the current Locator maps T## ranges to packet sections inside TECHNIQUES.md — sections that will no longer exist there. §4 step 3 prints only "a printed pointer to each family file" in the header, and step 4's re-pointing census covers inbound references from other surfaces, not the Locator's own entries. As drafted, the register's main routing instrument can survive the migration pointing at deleted sections. Cure C3 (in (3)-c).
- **D5 — No ten-word or phone check exists anywhere in the design or its migration Verify.** The migration census (§4 step 2) checks canonical counts, pointer counts, and pointer tier text; the pass condition (§4 step 6) checks capped-read size and the <60 s clock. Neither checks the pointer/index lines against the ten-word hygiene for card-like faces, nor any phone-width readability of the largest family file — the capped read (~50 KB) is a tool cap, not a phone measure. Cure C5 (in Further findings).

### (3) ANY POINT REDUCED? — YES — three points, one pixel counting

- **(3)-a EVIDENCE ONE STEP AWAY — REDUCED for 50 of 144 techniques.** Measured: 50 entries carry multiple Feeds. For every placement outside the canonical family, the reader's path becomes pointer → canonical family file → entry → packet frames: evidence is two hops from the family surface the reader is browsing, where today (single register + VIEWS lines carrying `P# @ timestamps`) it is one. The reduction compounds inside the canonical file itself: an entry's Feeds line names only `P# @ timestamps — ev/…`; the packet key resolving `P#` to a packet path lives in TECHNIQUES.md's header, which after the split is a different file from the entry — so even a canonical entry no longer carries its packet one step away. **Cure C1:** (i) pointer lines gain packet + timestamps (`T## · name · tier · P# @ range · canonical file`) — still one line, no mechanics duplicated, drift surface unchanged in kind; (ii) every family file's header carries the packet keys (the same block TECHNIQUES.md carries now), so an entry's `P#` resolves inside the file the reader is standing in.
- **(3)-b TIER ON EVERY LINE / ONLY RECREATED AS SUBSTRATE — REDUCED by separation.** Entry form is declared "unchanged," and in the current form a DESCRIBED not-owed entry carries no tier text in its own lines at all (verified on T26/T49: heading · mechanics · Feeds only; tier lives in the header counts and the tier register — the same file, today). After the split, the tier register stays in TECHNIQUES.md and the entry moves: a production reader standing in a family file meets DESCRIBED and IN PROGRESS entries with no tier on the entry and no substrate warning in the file (per D3, no family header is specified to carry one). That is precisely the failure A5's tier-on-every-line rule and the DLC absorption audit exist to prevent: non-RECREATED material readable as substrate because its tier is in another file. **Cure C2:** the design must amend the entry form for family files — tier printed on every canonical entry (heading suffix or a Tier line, OWED/not-owed mark included, mirroring the register) — and each family header must restate the tier counts for its canonical entries plus the line "only RECREATED is substrate; DESCRIBED / IN PROGRESS are inspiration." The migration census must check tier presence on every canonical entry, not only on pointer lines. ("Entry form unchanged" is thereby amended by name; the split changes what an entry must carry, because it changes what file the entry stands alone in.)
- **(3)-c GOVERNANCE SURFACE ROUTING — REDUCED by one unpriced hop.** The tier register (§2: every technique's tier + evidence + obligation) carries no canonical-family field, and per D4 the Locator's post-split target is unspecified. A reader who finds a technique in the tier register — the governance surface's main lookup — has no in-file route to its entry: they must guess the family or search seven files. Today that lookup is zero hops (same file). **Cure C3:** the post-split Locator maps each T## (or range) to its canonical family file, and each tier-register row (or its grouped rows) names the canonical family file; §4 step 2's census verifies every T## in the register resolves to exactly one canonical file via the Locator.

## Further findings

- **F1 (supporting, no severity) — The size case for the split is real and the fallback is unlikely to fire.** Reviewer's own estimate from the current register, canonical bytes by first-named Feeds: diagrams ≈19.3 KB · transitions ≈18.1 KB · word animation ≈10.1 KB · openings ≈11.8 KB (incl. variants) · endings ≈8.7 KB · cross-container ≈8.7 KB (incl. variants) · thumbnails <1 KB — every family far under one capped read even before pointer/header overhead. §4 step 6's pass condition is honestly stated and its packet-split fallback is a lawful last resort (container grouping survives at the top level), not a contradiction of §5's refusal.
- **F2 (MINOR) — A5 compliance is correctly carried, one wording debt.** §3 keeps VIEWS derived, same-cycle (migration step 5), Feeds fields as source of truth, and names the header update. Debt: A5's text defines VIEWS as generated "from TECHNIQUES.md Feeds fields"; after migration the Feeds fields live in the family files. The design says the source path changes, but the migration sequence should include amending A5's own wording in INSTRUCTION.md in the same cycle, or the instruction layer will describe a source that no longer exists (a stale-view path in the instruction layer itself).
- **F3 (MINOR) — Cure C5 for D5:** add to §4 a Verify line: pointer lines and family-file index/header lines counted against the ten-word limit for exposed card-like text, and the §4 step 6 naive-use test on the largest family file paired with one phone-width read of that file's head + one entry, printed as a spot check with its result — or the design explicitly prices the capped-read test as the phone proxy and names the residual risk. Silence on both is the defect; either act cures it.
- **F4 (MINOR) — Grouped tier-register rows vs "every technique's tier."** The current register groups some techniques into shared rows (e.g. T136/T138/T141–T144; T113–T121 groupings). §2's "every technique's tier + evidence + obligation mark" reads per-technique; if grouped rows carry over, the design should say so explicitly and C3's Locator becomes the per-technique instrument that makes grouping lawful.
- **F5 (no defect) — Refusals verified sound.** ASSETS.md left unsplit (26–31 KB, no measured cold-reader failure), the samples board kept as HQ's separate owed debt with the register readable without it, and entry duplication refused on drift grounds all match the owner's terms; the pointer mechanism itself is the right shape — its defect is only what the pointer omits (C1).
